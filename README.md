# Роздільнянський ковбасний цех

Вебсайт підприємства з каталогом ковбасних виробів і м’ясних делікатесів,
особистим кабінетом та системою заявок на продукцію.

**Сайт:** [rkc.com.ua](https://rkc.com.ua/)

**Контактна пошта підприємства:** [rkcvk.rozdilna@gmail.com](mailto:rkcvk.rozdilna@gmail.com)

Каталог та особистий кабінет доступні активним користувачам після входу.
Нові облікові записи потребують схвалення адміністратором.
Заявка передає менеджеру перелік продукції та контактні дані клієнта.
Наявність, вартість, строки виготовлення й умови отримання погоджуються з менеджером.
Онлайн-оплата не реалізована.

## Можливості

- Каталог активних товарів, фільтр категорій і пошук за частиною назви.
  Пошук працює незалежно від регістру українських літер: «Брест», «брест» і «БРЕСТ»
  повертають однакові результати. Спецсимволи запиту сприймаються як звичайний текст.
- Пагінація по 24 товари зі збереженням пошукового запиту та категорії.
- Сторінка товару зі складом, харчовою й енергетичною цінністю та умовами зберігання.
- Випадкова добірка до 8 активних товарів на головній: спочатку обираються товари
  з різних категорій, потім випадковими товарами заповнюються решта місць.
- Обрані товари: додавання й видалення без перезавантаження сторінки,
  оновлення сердечка та видалення картки зі списку обраного.
- Кошик у сесії: від 0,01 до 1000 кг або від 1 до 1000 цілих штук на позицію.
  Один товар у кг та шт зберігається як дві окремі позиції.
  Лічильник у шапці показує кількість доступних позицій, а не суму кг і штук.
- Додавання до кошика без перезавантаження, повідомлення та анімація польоту фото.
  Без JavaScript додавання до кошика й робота з обраним виконуються звичайним POST.
- Особистий кабінет із редагуванням імені, прізвища й телефону, історією заявок,
  повторенням попередньої заявки та скасуванням нової.
- Листи менеджеру й клієнту, кольорові статуси та шкала опрацювання заявки.
- Адмінпанель Django Unfold: керування каталогом, користувачами, зверненнями та заявками.
- Український інтерфейс, локальні переклади адмінпанелі, favicon, адаптивне оформлення,
  слайдер добірки, анімації появи й лічильників із підтримкою `prefers-reduced-motion`.
- Повідомлення з ручним закриттям і автоматичним приховуванням через 60 секунд:
  повтори об’єднуються, одночасно показується не більше двох.
- Політика конфіденційності, доступна до входу, та обов’язкова галочка ознайомлення
  під час реєстрації. Форма не приймається без її встановлення.

## Локальний запуск у Windows та PyCharm

Наведені кроки призначені для **нової локальної копії**. Для вже налаштованого проєкту
використовуйте наявне оточення та `.env`; повторно створювати їх не потрібно.

### 1. Отримати код і встановити залежності

Потрібні Git та Python 3.12 або новіший. У PowerShell:

```powershell
git clone https://github.com/RadmilaVodopianova/RKC_final_project.git RKC_Final_project
cd RKC_Final_project
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

У PyCharm відкрийте папку з `manage.py` та виберіть інтерпретатор
`.venv\Scripts\python.exe`.

Активація оточення в PowerShell:

```powershell
.\.venv\Scripts\Activate.ps1
```

Якщо PowerShell забороняє запуск цього сценарію, можна виконувати всі подальші
команди через `.\.venv\Scripts\python.exe` замість `python`, без активації.

### 2. Створити локальний `.env`

Наступна команда створює `.env` з прикладу та генерує окремий секретний ключ.
Режим `x` не дозволяє перезаписати вже наявний файл.

```powershell
python -c "from pathlib import Path; import secrets; content=Path('.env.example').read_text(encoding='utf-8'); content=content.replace('replace-with-your-own-secret-key', secrets.token_urlsafe(64)); file=Path('.env').open('x', encoding='utf-8', newline='\r\n'); file.write(content); file.close(); print('.env створено')"
```

Локально залиште `DEBUG=True`, `HTTPS_ENABLED=False` та консольний поштовий backend.

### 3. Підготувати базу та статику

```powershell
python manage.py migrate
python manage.py createsuperuser
python manage.py collectstatic --noinput
python manage.py check
```

Під час створення адміністратора зазначте email: він потрібен для входу через
форму сайту. Пароль введіть у терміналі; він не відображатиметься.

`collectstatic` потрібно виконати перед перевірками сторінок і тестами,
оскільки застосунок використовує маніфест статичних файлів.

### 4. Заповнити каталог і підготувати фотографії

Для **нової порожньої бази** можна завантажити початковий набір:

```powershell
python manage.py loaddata core/fixtures/catalog.json
```

У наборі 7 категорій та 89 товарів. Робочий каталог може відрізнятися:
його актуальний стан зберігається в базі даних.

**Не запускайте цю команду для робочої бази з реальними даними.** Записи з однаковими
первинними ключами можуть бути перезаписані. Для продовження роботи з чинним
каталогом потрібна узгоджена резервна копія бази та фотографій.

Створіть папку оригіналів, якщо її ще немає:

```powershell
python -c "from pathlib import Path; Path('media/products').mkdir(parents=True, exist_ok=True)"
```

Порядок додавання фотографій описано в наступному розділі.

### 5. Запустити сайт

```powershell
python manage.py runserver
```

Відкрийте [127.0.0.1:8000](http://127.0.0.1:8000/).
До входу відображається сторінка доступу. Увійдіть email і паролем створеного
суперкористувача. Панель адміністратора: [127.0.0.1:8000/admin/](http://127.0.0.1:8000/admin/).

`runserver` використовується лише для локальної розробки. На робочому сервері
застосунок запускає Gunicorn через systemd.

## Каталог і фотографії

Оригінали `media/products/` виключені з поточної опублікованої історії Git.
**`git clone`, `git pull` та `collectstatic` не завантажують фотографії товарів.**

Для локальної копії доступні два способи:

1. Додати фотографії через поле «Фото товару» в адмінпанелі.
2. Скопіювати оригінали з резервної копії в `media/products/`, зберігаючи точні
   назви та вкладені папки. Поле `Product.image` містить відносний шлях,
   наприклад `products/001_Брестська_1с.вар.png`; самі байти фото зберігаються на диску.

Без вибраної фотографії картка показує заглушку. Якщо база містить шлях до файлу,
а файла немає на диску, потрібно відновити його або вибрати інше фото в адмінпанелі.

Для карток створюються WebP-прев’ю шириною до 360, 720 та 1080 px з пропорцією 4:5.
Розмір обмежується оригіналом, використовується `srcset`.
Кеш лежить у `media/catalog_thumbnails/` і не входить у Git.
Оригінали не перезаписуються. За помилки створення прев’ю використовується URL оригіналу.

Після завантаження нового фото на робочий сайт локальна копія цього фото
автоматично не з’явиться — медіафайли синхронізуються окремо від коду.
Логотип, банер, іконки та зображення оформлення в `static/images/` залишаються в репозиторії.

## Налаштування оточення

Файл `.env` знаходиться поруч із `manage.py`. Значення змінних середовища процесу
мають пріоритет над значеннями з `.env`.

| Змінна | Призначення |
| --- | --- |
| `SECRET_KEY` | Обов’язковий приватний ключ Django; окремий для кожного оточення |
| `DEBUG` | Локально `True`, на робочому сервері `False` |
| `ALLOWED_HOSTS` | Імена хостів через кому, без протоколу та шляху |
| `HTTPS_ENABLED` | Увімкнення HTTPS-перенаправлення, захищених cookie та HSTS |
| `MAIL_BACKEND` | Консольний або SMTP-backend пошти |
| `DEFAULT_FROM_EMAIL` | Ім’я та адреса відправника |
| `MANAGER_EMAIL` | Адреса отримувача повідомлень менеджеру та адреса відповіді клієнта |
| `SMTP_HOST`, `SMTP_PORT` | Поштовий сервер і порт |
| `SMTP_USERNAME`, `SMTP_PASSWORD` | Облікові дані SMTP, зокрема окремий пароль додатка Gmail |
| `SMTP_USE_TLS`, `SMTP_USE_SSL` | Режим шифрування; обидва значення не можуть бути `True` одночасно |
| `SMTP_TIMEOUT` | Додатний тайм-аут SMTP у секундах |

Для робочого домену використовується `ALLOWED_HOSTS=rkc.com.ua,www.rkc.com.ua,127.0.0.1,localhost`.
`HTTPS_ENABLED=True` слід вмикати лише за налаштованим HTTPS-проксі Nginx,
який сам встановлює правильний `X-Forwarded-Proto`.
Застосунок довіряє цьому заголовку; прямий зовнішній доступ до порту Gunicorn має бути закритий.

## Електронна пошта

Для локальної розробки використовуйте:

```dotenv
MAIL_BACKEND=django.core.mail.backends.console.EmailBackend
```

Листи в цьому режимі друкуються в терміналі та не надсилаються адресатам.

На робочому сайті використовується заводська скринька Gmail. У `.env` налаштовуються:

```dotenv
MAIL_BACKEND=django.core.mail.backends.smtp.EmailBackend
SMTP_HOST=smtp.gmail.com
SMTP_PORT=587
SMTP_USERNAME=rkcvk.rozdilna@gmail.com
SMTP_USE_TLS=True
SMTP_USE_SSL=False
SMTP_TIMEOUT=15
DEFAULT_FROM_EMAIL="Роздільнянський ковбасний цех <rkcvk.rozdilna@gmail.com>"
MANAGER_EMAIL=rkcvk.rozdilna@gmail.com
```

Окремо приватно заповніть `SMTP_PASSWORD` паролем додатка Google для цієї скриньки.
Справжнє значення не публікуйте в документації, скриншотах або командах із відкритим паролем.
Після зміни серверного `.env` перезапустіть службу `rkc`.

У цій версії Django використовується налаштування `MAILERS["default"]`,
сформоване з `MAIL_BACKEND` та `SMTP_*`. Відправлення викликається через `.send(using="default")`.

| Подія | Лист клієнту | Лист менеджеру |
| --- | --- | --- |
| Створення заявки | Підтвердження, перелік товарів і посилання на заявку | Нова заявка та контакти клієнта |
| Реальна зміна статусу | Повідомлення про новий статус | Окремий лист передбачено для скасування |
| Перехід у «Скасована» | Повідомлення про скасування | Контакти, попередній статус і перелік товарів |
| Повторне збереження того самого статусу | Новий лист не створюється | Новий лист не створюється |

Повідомлення про створення та зміну статусу надсилаються після успішного завершення
транзакції бази. Збій SMTP не скасовує збережену заявку; помилка потрапляє в журнал.
Автоматичної черги повторного надсилання немає.

## Доступ користувачів

До входу доступні сторінки входу, запиту на реєстрацію та політики конфіденційності,
а також потрібні для їх оформлення ресурси.
Каталог, кошик, обране, кабінет і `/media/` захищені middleware.
Один вхід відкриває сайт і особистий кабінет — друга авторизація не потрібна.

Щоб схвалити користувача:

1. Увійдіть до `/admin/` як адміністратор.
2. Відкрийте розділ користувачів.
3. Виберіть новий неактивний обліковий запис і дію **«Схвалити доступ до сайту»**
   або встановіть для нього ознаку **«Активний»** у формі редагування.
4. Повідомте користувача про схвалення. Автоматичного листа про схвалення не реалізовано.

Для звичайного клієнта достатньо `is_active=True`.
`is_staff` та `is_superuser` надають адміністративні можливості й не потрібні для перегляду каталогу.
Деактивація облікового запису припиняє доступ через перевірки автентифікації та middleware.

Нові користувачі входять за email. Для наявних адміністраторів backend також підтримує
старий логін без символу `@` у формі входу Django admin.
Галочка ознайомлення з політикою перевіряється формою реєстрації;
окремий журнал версій політики та підтверджень у базі не ведеться.

## Робота із заявками

| Код статусу | Назва в інтерфейсі |
| --- | --- |
| `new` | Нова |
| `processing` | В обробці |
| `confirmed` | Погоджена |
| `completed` | Виконана |
| `cancelled` | Скасована |

Номер `customer_number` формується окремо для кожного користувача.
Внутрішній ID бази може відрізнятися від номера, який бачить клієнт.
Заявка зберігає назви товарів і контактні дані на момент надсилання;
подальші зміни каталогу або профілю не оновлюють цей знімок автоматично.

Користувач бачить лише власні заявки. Доступ до чужої заявки повертає 404.
Скасування доступне власнику лише зі статусу «Нова» та виконується POST-запитом.
Повторення додає доступні товари до поточного кошика, повідомляє про пропущені позиції
й не створює нової заявки до окремого оформлення.

Адмінпанель містить фільтри статусів і дат, пошук, кількість позицій та масові дії
«В обробці», «Погодити», «Скасувати».
Змінюйте статус через форму або ці дії, щоб запускалися сигнали листування.
Масові дії зберігають кожну змінену заявку через
`save(update_fields=["status", "updated_at"])`.
Пряме оновлення статусу через `QuerySet.update()` оминає ці сигнали.

## Перевірки

У локальному оточенні з консольною поштою та `HTTPS_ENABLED=False`:

```powershell
python manage.py collectstatic --noinput
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py test
python -m unittest discover -s deploy -p "test_*.py"
```

На момент підготовки README команда Django знаходить 125 тестів.
Ще 9 перевірок резервного копіювання запускаються окремою командою `unittest` вище.
Тести Django створюють окрему тестову базу, тести резервного копіювання — тимчасові файли.
Окремі перевірки символічних посилань можуть пропускатися, якщо система
не дозволяє створювати такі посилання.

Покриті сценарії: email-вхід і схвалення доступу, приватні сторінки й медіафайли,
політика та галочка реєстрації, кошик у кг/шт і його ліміти, нумерація та знімки заявок,
доступ до чужих заявок, повторення та скасування, листи й SMTP-налаштування,
обране без перезавантаження, пошук кирилицею, пагінація, прев’ю зображень
і перевірка цілісності резервних архівів.

Після змін інтерфейсу додатково перевіряйте ширини 360, 768 і 1280 px,
роботу клавіатури, режим зменшення руху, повідомлення, кошик та обране.
Адаптивність на справжньому iPhone перевіряється окремо від емуляції браузера.

## Оновлення налаштованого сервера

Робоче розгортання: Ubuntu 24.04 LTS на VPS «Хостінг Україна»,
Gunicorn під користувачем `rkc`, Nginx із HTTPS, служба systemd `rkc`.
Проєкт розташований у `/home/rkc/app`, оточення — `.venv`,
Gunicorn слухає лише `127.0.0.1:8000`.

Наведені команди призначені для вже налаштованого VPS. Основна служба `rkc`,
конфігурація Nginx і сертифікати налаштовані на сервері та не створюються командами нижче.
У репозиторії є systemd-файли лише для резервного копіювання.

Перед оновленням переконайтеся, що зміни перевірені локально, закоммічені та відправлені,
а серверна робоча папка не містить неврахованих змін:

```bash
cd /home/rkc/app
source .venv/bin/activate
git status --short
```

Після перевірки стану виконайте:

```bash
sudo systemctl start rkc-backup.service &&
git pull --ff-only &&
python -m pip install -r requirements.txt &&
python manage.py check &&
python manage.py makemigrations --check --dry-run &&
python manage.py collectstatic --noinput &&
HTTPS_ENABLED=False MAIL_BACKEND=django.core.mail.backends.console.EmailBackend python manage.py test &&
python manage.py migrate --noinput &&
sudo systemctl restart rkc &&
sudo systemctl is-active rkc
```

Знаки `&&` зупиняють наступні дії за помилки. Тимчасові змінні перед командою тестів
діють лише для цього процесу: серверний `.env` і налаштування запущеної служби не змінюються.
Не створюйте нові міграції на сервері — застосовуйте вже перевірені файли з репозиторію.

Очікуваний стан служби після оновлення — `active`.
Відкрийте сайт, перевірте вхід, каталог і фотографії. Перед перевіркою листів
на реальних адресатів погодьте тестову заявку з менеджером.

Діагностика:

```bash
sudo systemctl status rkc --no-pager -l
sudo journalctl -u rkc -n 50 --no-pager
sudo nginx -t
```

Не додавайте в Nginx відкритий `alias` або `root` для `/media/` чи захищених зображень
оформлення. У поточній схемі запити мають проходити перевірку доступу Django;
WhiteNoise розташований після middleware схвалення доступу.

## Резервні копії

[deploy/backup.py](deploy/backup.py) створює архів із такими даними:

- узгоджений знімок SQLite через online backup API, включно із закомміченими даними WAL;
- приватний `.env`;
- оригінали `media/products/`;
- опис архіву й контрольні суми SHA-256 кожного файла.

Перед завершенням перевіряються цілісність знімка SQLite та вміст архіву.
Зберігаються останні 7 успішних архівів; сторонні файли в папці не видаляються.
Кеш прев’ю, код, віртуальне оточення, конфігурація Nginx і сертифікати до цих архівів не входять.

Налаштований серверний таймер запускає копіювання щодня о **03:30 за Europe/Kyiv**.
Після пропущеного запуску використовується `Persistent=true`.

```bash
sudo systemctl start rkc-backup.service
sudo journalctl -u rkc-backup.service -n 12 --no-pager
sudo systemctl list-timers rkc-backup.timer --no-pager
ls -lh /home/rkc/backups
```

Ручне створення копії поза папкою проєкту:

```bash
python deploy/backup.py --backup-dir /home/rkc/backups --keep 7
```

Архіви містять приватні дані та потребують захищеного зберігання.
Періодично завантажуйте перевірену копію на окремий захищений носій:
автоматичне копіювання за межі VPS не реалізоване.
Повне відновлення виконується окремою контрольованою процедурою із збереженням
поточного стану та зупиненням служби; автоматичного сценарію відновлення немає.

## Приватні дані та Git

У Git зберігаються код, шаблони, статика оформлення, міграції та початкові дані каталогу.
Правила [.gitignore](.gitignore) виключають:

- `.env` та його приватні варіанти; `.env.example` залишається в репозиторії;
- SQLite-бази, їхні службові файли та варіанти назв резервних копій;
- оригінали фото каталогу та кеш прев’ю;
- віртуальні оточення, `staticfiles/`, кеші Python і файли IDE;
- папки локальних резервних копій, журнали та визначені формати приватних ключів.

Перевірка правила навіть для раніше відстежуваних шляхів:

```bash
git check-ignore --no-index --verbose .env db.sqlite3 media/products/test.jpg
git ls-files media/products
git status --short
```

`git ls-files media/products` не повинен повертати файлів.
Сам `.gitignore` не приховує вже відстежувані файли та не видаляє попередні версії з історії.
Папку каталожних фотографій виключено з опублікованої історії окремою операцією.
Старі копії репозиторію з попередньою історією потребують узгодження перед подальшою
роботою: не об’єднуйте та не публікуйте їхню стару історію повторно.

Перед коммітом переглядайте вибрані файли. Приватні архіви, база, паролі й секретні ключі
не повинні потрапляти в репозиторій або вкладення до публічних issue.
У разі оприлюднення секрету його потрібно замінити; видалення файла з поточної версії недостатньо.

## Типові труднощі

| Ситуація | Що перевірити |
| --- | --- |
| `No module named django` | Інтерпретатор `.venv` та встановлення `requirements.txt` у це оточення |
| `Set the SECRET_KEY environment variable` | Наявність `.env` поруч із `manage.py` і заповненого `SECRET_KEY` |
| `.env` уже існує | Збережіть наявні налаштування; команда створення навмисно не перезаписує файл |
| `DisallowedHost` | Ім’я хоста в `ALLOWED_HOSTS` без `http://`, порту та шляху |
| Сайт просить увійти в приватному вікні | Це очікувана поведінка закритого сайту |
| Новий користувач не може увійти | Схвалення адміністратором, `is_active`, правильні email і пароль |
| Немає фото після клонування | Окреме перенесення `media/products/` та відповідність назв шляхам у базі |
| `Missing staticfiles manifest entry` | Наявність вихідного ресурсу та повторний `collectstatic --noinput` |
| Листи є в терміналі, але їх немає у скриньці | Консольний backend; для справжнього надсилання потрібні SMTP-налаштування |
| Помилка Gmail або лист не надійшов | Пароль додатка, SMTP-налаштування, папка «Спам» і журнал служби `rkc` |
| Локальний HTTP перенаправляється на HTTPS | `HTTPS_ENABLED=False` для локального запуску та перезапуск процесу |
| `git pull --ff-only` відхилено | Звірте історію й локальні зміни; збережіть їх перед будь-яким виправленням |
| Фото завантажено через адмінку, але його немає в Git | Це очікувано: оригінали й резервні копії передаються окремо від коду |
